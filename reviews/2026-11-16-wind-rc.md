## 3. Hub (0.6.16), against proposal §2, §11.2 and §11.3

- **Scheduled path:** last line of the hourly job, after Sun face. With `WIND_ENABLED` unset it returns "wind:not scheduled (WIND_ENABLED unset)" and makes no request, writes nothing and adds no run row. On a manual hourly run it is skipped.
- **Manual path:** `/admin/run/wind` with the admin key runs the collector once whatever the flag says; without the key, 403 and no request.
- **Finding the run:** candidates newest first, four back. The search stops at the run already published without asking. A 404 on an index means "not there yet"; any other non-200, or an index over 200 KB, is a failure.
- **Six fields:** index parsed for exactly one line each (`anl` only); one object check for size and ETag; each range refused before its body is read unless 206 with the exact Content-Range, length and ETag; body length checked again after reading. Every request has a 30-second limit.
- **Decoding:** one field at a time; the decoder's own refusals are named failures ("field refused by the decoder"), with the reason in the run row.
- **Grids:** `wind/grids/<sha256>.i16`, written create-only, read back and hashed. An existing object is used only if it hashes to its name; otherwise the run fails and the object is left alone.
- **Manifest:** `wind/current.json` holds current and previous. Every write is conditional (create-only for the first, ETag match after). A lost write is re-read and advanced only if the candidate is still newer. A late older run is logged "superseded" and changes nothing.
- **Failures:** the manifest keeps both revisions and gains `last_attempt` (run, reason, count, and the first time that run's index was seen, which survives repeated failures and becomes the revision's `index_first_seen` when it finally publishes).
- **Nothing is deleted.** There is no delete call in the wind code.
- **Routes:** `/snapshot/wind/meta`; `/snapshot/wind/grid/<sha256>.i16` only for hashes named by current or previous, and only if the stored bytes hash to the name (else 503 "integrity").
- **Three times in every published revision and its run row:** index first seen, fields fetched, published.

## 4. Page, against proposal §4 and §11

- **Off on load; no request while off.** On: the manifest, then one grid.
- **Its own transparent sheet** (the Ocean Heat and Dust RGB method), beneath both. It does not use the globe's picture.
- **One canvas carries colour and arrows.** One colour per model cell, no smoothing, so the colour at a place is the scale colour of the number the reading gives. Arrows every 5°, thinned toward the poles, none beyond 80°; a dot where it is calm; a hatch where there is no value.

- **Height control** is a radio group. The checked button, the sheet, the valid-time line and the point reading change in one step. A height that is loading is marked pending and the previous one stays. A height that fails is named: "Stratosphere could not be loaded: … Still showing Near ground."

It reads the nearest whole-degree model cell and names it. "From west (270°), 18 km/h"; "Calm (under 1 km/h)."; "No model value here."; at a pole, speed and "No compass bearing at the pole."
- **Revisions:** a height switch keeps the run already shown. A newer run arrives on the 10-minute refresh as one step. A manifest naming an older run is ignored. If the run shown has aged out (404), the manifest is read again and everything moves together.
- **Age** from valid time. At 24 hours the sheet is cleared and the card says why. Rechecked on a 30-second tick and when the tab returns. No "stale" label exists.
- **Wording:** "Modelled" tag (dashed, the page's computed style); "Modelled wind · NOAA GFS · Valid at …"; "not a measurement, not a forecast"; "sampled to 1° and quantised by Mother Earth".

## 8. GPT's stage 2 review of `0cecbe1` (relayed by Chad, 16 Nov) — rev 2

GPT: hold stage 3 for a hub fix. The R2 grid publication and the scheduler gate passed review; GPT reran the 87 hub checks with the saved NOAA sample. Two failures reproduced that the branch suites missed. Both are confirmed and fixed.

### 8.1 Status on the manifest when runs overlap (hub)

**GPT's findings:** an older run that fails after a newer run has published could put the "latest update did not complete" note back; an older scan that found no new index could erase a newer failure and its `index_first_seen`. The published grids were not affected in either case.

**Cause:** `last_attempt` was written and cleared with no ordering, and the first sighting of a run's index was stored inside it, so clearing one lost the other.

**Fix, in the conditional manifest update itself:**
- **A failure note is ordered.** A note that names a run is kept only while that run is newer than the published one. A note that names no run (the index could not even be asked for) is kept only if its attempt started after the published revision's. A note is never replaced by an attempt that started earlier. (`windNoteRelevant`.)
- **A failure that is not noted is still in the run rows,** marked "(not noted on the manifest: a newer result is already there)".
- **A clean scan clears only an earlier note.** A note from an attempt that started later stays.
- **The sighting has its own field, `seen`** (`{ run, index_first_seen }`). It is written as soon as an index is found, before anything else can fail. A newer run replaces it; for the same run the earlier time is kept; nothing but the publication of that run (or a newer one) clears it. (`windSeenMerge`.)
- **At publication** the revision takes the earliest sighting on the manifest at commit time, and any note that is no longer about something newer is dropped.

**Both completion orders are tested** (hub suite section H, 14 checks): the earlier run fails after the later one publishes, and the reverse; the older clean scan ends after the newer failure, and the reverse; a later clean scan clears an earlier note and an earlier one does not; a sighting recorded by another attempt after this run read the manifest is the one published. Breaks: `note-unordered`, `clear-newer-note`, `late-note-kept`, `seen-in-note`.

### 14.3 REGISTER wording, drafted — **not filed; filing is its own Approve line**

> **NOAA/NCEP Global Forecast System (GFS) — wind at three heights (modelled; optional layer).** Source: NOAA Open Data Dissemination (NODD) on AWS, bucket `noaa-gfs-bdp-pds`, 0.25° pressure GRIB2, analysis hour f000; six fields a run (eastward and northward wind at 10 m above ground, 250 hPa and 10 hPa), fetched by byte range, about 4 MB a run. Requests: a successful fetch of one run is eight (one index, one object check, six ranges), after one index lookup for each newer candidate run not yet on the mirror; no retries inside a run. On an hourly check with nothing new: one index lookup for each candidate run newer than the one held (up to four are tried, newest first; several are possible when the held run is more than one cycle behind), or none while the newest possible run is already held. NOAA produces a run every six hours. Terms read 16 Nov 2026 at registry.opendata.aws/noaa-gfs-bdp-pds: "open to the public and can be used as desired"; NOAA requests attribution "for the use or dissemination of unaltered NOAA data"; no stated or implied endorsement by or affiliation with NOAA; modified data must not be stated or implied to be original, unaltered NOAA data. What Mother Earth shows is modified, so the attribution request does not strictly reach it; the credit "NOAA/NCEP GFS" is kept all the same, always together with the disclosure that Mother Earth resamples the grids (the value at each whole degree, to 1°) and quantises them (to 0.1 m/s), and that they are not original, unaltered NOAA data. Commercial use: the terms place no restriction; no endorsement, no logo. Not read: a NOAA-hosted page of terms for GFS output specifically.
